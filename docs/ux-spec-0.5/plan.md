# Plan picker, Run and Edit: 0.5 UX spec

This is the Phase B spec (B1a) for the plan picker and a plan's Run and Edit views. Its structure and binding decisions come from `.superpowers/sdd/review-everything-e2e-to-sequential-cascade/spec-template.md`. Source paths are relative to `frontend/map-studio-v4/` unless prefixed, and audit IDs come from `docs/ux-audit-0.5/`. Sibling specs are referenced, not restated: `room-schedule.md` (the Schedule block inside an Edit row, its copy and Reset), `home-rooms.md` (home plan card, `v4_room_setting_*` keys, `v4_room_parts`), `shell.md` (status strip, Stop place, notice rule, toast, dialogs, detents) and `design-system.md` (tokens, sizing, disabled buttons).

## 1. Scope
- **Surfaces:** the picker (`workflow: "plans"`); a plan's Run and Edit views (`workflow: "plan"` plus a new substate, `planView: "run" | "edit"`); the Edit room list and its rows; and the feedback for Save, Delete, running the plan and Run's "Plan enabled" switch.
- **Audit IDs:** MS-PLANS-01 to 05; MS-PLAN-01, MS-PLAN-02, MS-PLAN-04 to 06, MS-PLAN-09 to 13, MS-PLAN-15 to 20, MS-PLAN-22; MS-KEY-01 (plan side).
- **Owner decisions touched:** the Apple-level bar; refine `ms-*`; Stop in its invariant place without confirmation (`shell.md` §3); the shell invariants; and `planView` as a substate rather than a new workflow.

## 2. User goal
A household administrator with saved plans wants to see what a plan's next run will clean, start it with one tap, and now and then change its rooms or order. Within two seconds they must see which rooms run next and with which settings, what extra work is due, whether Run plan will work, and, if it won't, which room needs fixing.

## 3. Hierarchy
- **Picker** (390: sheet at half; 1024: inspector), top to bottom: a plain back chevron named "Back to all tasks" and the h2 "Your plans" → the notice slot (`shell.md` §4 rule 2) → the description → plan rows, default plan first, then catalog order. Line 1: the name, plus a "Default" chip for `PlansCatalog.selectedPlan` (backend-contracts.ts:258). Line 2, one whole string by order: "{count} rooms · Longest-waiting rooms first" or "{count} rooms · Top to bottom, as listed". An optional line 3 (`--ms-t-xs`, `--ms-text` with a tone glyph, never raw tone-coloured text, `design-system.md` §5): the due lines, one complete string per due kind with the due glyph ("Mop due in Kitchen and Study", "Heavy duty vacuum due in Living room"; from `nextRunPreview.rooms[].cadenceReasons`, the level from that room's `coverageSetting`, backend-contracts.ts:180-181), or "Needs attention before it can run" with the warning glyph for any blocker except `plan_disabled`. A paused plan (`enabled: false`) shows one status only: a "Paused" chip on line 1 and no line 3. Each row ends in a chevron. The last row is "Create a plan" (plus glyph, secondary-row style). There is no primary action: `choose-cleaning` (state.ts:1072-1080) stays hidden (shell.ts:948). With no plans, one card shows "No plans yet", the hint, and a filled "Create a plan" button as the only action.
- **Run view** (390: half; 1024: inspector), top to bottom: a plain back chevron named by origin ("Back to all tasks" from the home plan card, "Back to plans" from the picker), the h2 (plan name, one line, ellipsis) and a trailing "Edit" text button → the notice slot → the summary "{count} rooms", or "{count} rooms · about {minutes} min" with §9, each one string (the hint or the numbers show the order) → the due lines directly under the summary (picker line 3's family, 1–4 lines, no live role) → "Next run" ("After this run" while `resources.entry.activePlan`, backend-contracts.ts:41): rows from `nextRunPreview.rooms` in server order. Saved order is an `<ol>` numbered 1…n; Intelligent rotation is a `<ul>` without numbers under the one hint line "Longest-waiting rooms first, rechecked when you run the plan.". Each row shows the name and its effective setting (`v4_room_setting_*`, `home-rooms.md`, which already reads the due work), with no chip except "Needs attention". When `missionBoundaries` is not empty, the `v4_room_parts` line (`home-rooms.md`) sits above the list, with a plain divider at each boundary; the old per-part caption goes. When paused, the list is headed "Rooms in this plan" and shows `SavedPlan.rooms` in saved order, unnumbered, with no chips and no Try again → the "Plan enabled" switch row, with its hint as the description; the switch is off when the plan is paused → one quiet "When a run ends" line → the sticky action bar: **Run plan**, with its reason shown when it is disabled. Stop follows `shell.md` §3: at narrow widths it takes the bar's primary slot while work is stoppable; at wide widths it sits in the status strip (shell.ts:1317-1320) and the bar shows no primary.
- **Edit view** (390: full; 1024: inspector), top to bottom: the h2 "Edit plan" ("New plan" when new), with an "Unsaved changes" chip inside it while `planDraft.dirty`, and a trailing "More actions" overflow holding "Delete" (absent when new, disabled with its reason while dirty) → the notice slot → "Plan name" → "Cleaning order", a segmented control [Intelligent rotation | Saved order] with a one-line hint → "Rooms" with "{selected} of {total} selected", where the limit reason sits once 100 rooms are selected → the room list: selected rooms in plan order, then the rest in map order → "When a run ends" (a collapsed disclosure) holding, in order, the switch "Return to the dock when finished", the switch "Finish the current room when you press Stop" with its hint, and, only while that is on, the slider "Finish if at least {percent}% done" (0–100, step 5) → the sticky bar: **Cancel** (secondary, start side) and **Save** or **Done** (primary, end side). Edit has no next-run section (MS-PLAN-17). The header back button is hidden; Cancel replaces it. While work is stoppable, Stop takes the primary slot at narrow widths. At wide widths Stop is in the strip, and the bar holds Cancel and "You can save when the robot finishes."
- **Edit room row.** An `.ms-row` (`design-system.md` §4) whose label part is a disclosure button rather than the `.ms-check` label that Rooms uses (`home-rooms.md`), so on a selected row a tap on the name expands it here and never selects it. A selected row, inline start to end: a 44×44 checkbox named "Include {room}", which is its own target (no `<label>` wraps the row) · one disclosure button spanning the row up to the arrows, with `aria-expanded`, named "Settings for {room}" (`v4_room_settings_named`, defined in `home-rooms.md`), which holds the position number (Saved order only), the name (`<bdi>`), line 2 with the room's own cleaning mode and vacuum coverage from the draft (`v4_room_setting_*`, `home-rooms.md`; the preview's effective setting stays in Run and Rooms), line 3 with the schedule text at `--ms-t-xs` (`v4_room_schedules_*`, only while a schedule is on), "Needs attention" as the only chip, and the `ms-*` chevron · in Saved order only, "Move earlier" and "Move later" as separate 44 px buttons outside the disclosure. An unselected row shows only the checkbox and the name, and its body is inert. Expanded: the "Cleaning mode" and "Vacuum coverage" selects, then the Schedule block (`room-schedule.md`). The room card is the only bordered container (the `design-system.md` nesting rule).

## 5. Interaction
- **State (frontend only).** Add `WorkspaceState.planView: "run" | "edit"` and `planOrigin: "home" | "plans"` (contracts.ts:200-237). `planView` rule: `select-plan` (state.ts:517-526) and `selectPlan` (effects.ts:2096-2106) open Create (`planId: null`) in `"edit"`; they set `"run"` when a different saved plan is selected or the plan workflow is entered; reselecting the open plan, as the reset reload does (effects.ts:2504), keeps the view. Leaving the plan workflow resets it to `"run"`: `open-workflow` (state.ts:291-298), `discard-draft` (391-399) and `dismiss-top-layer` (557-571). `open-workflow` for `"plan"` itself (Try again, workflow-panel.ts:217) keeps it. The home plan card sets `planOrigin: "home"`; a picker row or Create sets `"plans"`. Two new intents: `set-plan-view {view, roomId?}` and `set-plan-enabled {enabled}`.
- **Selector.** There is one routing rule: the plan branch takes `save-plan` when `planView === "edit" || dirty || !id` (state.ts:1005), and `run-plan` otherwise. There is also one enable change: the `save-plan` branch's `enabled` (state.ts:1017) gains `command !== "pending"`. That is strictly narrower and fail-closed; today only the silent refusal at effects.ts:2587 stops a second tap. Branch order stays, and everything else is a label or reason change. The button reads "Done" when `id && !dirty`, otherwise "Save". While a plan save is pending it is disabled, keeps its label, and gives "Waiting for Home Assistant to save the plan." "Waiting for the map to be ready." appears when `canEditCoordinates` fails (state.ts:1008). Blockers get their own `{room}` reasons.
  - A new `pendingAction: "run-plan" | "save-plan" | null` is set with `command: "pending"` (effects.ts:2406 for the preflight, 2593 for saves) and cleared with it. R6's reason replaces only `motionBlockReason`'s final fallback, "Waiting for the current robot operation to finish." (state.ts:795-798), and only while `pendingAction === "run-plan"`; the switch and Run's Edit button are then disabled with the same reason. While it is `"save-plan"`, Run plan (through the same fallback), Save, the switch and Run's Edit button give "Waiting for Home Assistant to save the plan." When disabled, the switch, Edit, Save and Delete show their reason on a description line directly under them (`aria-describedby`, the `design-system.md` disabled-with-reason pattern); range ends do not (`design-system.md` §4).
  - `PrimaryAction` (contracts.ts:307-317) gains the placeholders that `home-rooms.md` adds, and an optional `jump {labelKey, roomId}`, rendered as a 44 px link inside `.action-reason` (shell.ts:959-963). The `save-plan` handler, which always calls `savePlan` today (effects.ts:2477-2479), dispatches `set-plan-view run` without a service call when the draft is clean. It also dispatches `set-plan-view run` after a successful save (effects.ts:2344).
- **In-place reloads.** `loadPlans` gains a keep-catalog mode. Today it sets `plans` to loading with a null catalog (effects.ts:2041-2043), and `#resource` then replaces the whole Run/Edit body (workflow-panel.ts:208-211, 623). The run-plan preflight's reload (effects.ts:2411), the switch's reloads and Reset's reload (effects.ts:2499, `room-schedule.md` S13) use the new mode, so `plans.status` stays ready, the view stays mounted, focus is kept, and 954-963 never pre-empts R6.
- **Run switch** (the one new effect). "Plan enabled" applies at once.
  - **Draft.** `set-plan-enabled` patches `planDraft.enabled` with `dirty: false`, so Run plan and the preflight, which read it (state.ts:1034, 1037; effects.ts:2393), follow the switch at once. A failure reverts it. There is no reselect: `savePlan`'s reconcile matches only the same draft object (effects.ts:2333-2344), and the switch does not use it.
  - **Request.** The effect, not the tap, sets `command: "pending"` and `pendingAction: "save-plan"` once, before the reload, and holds them until the save settles. It calls the service the way `#serviceMutation` does but without that function's pending refusal (effects.ts:2587), which is therefore unreachable. It first reloads the catalog in place, then sends `save_plan` with the request `savePlan` builds (effects.ts:2299-2324) from that fresh saved plan, with only `enabled` changed. The payload shape is unchanged. Because `save_plan` replaces the whole plan with no version check (effects.ts:2301-2324), an edit made elsewhere between the reload and the send can still be overwritten, including a shared schedule update (plans.py:2474-2480). §9 lists the backend fix.
  - **Disabled reasons, first match wins, each on the switch's description line:** while `pendingAction === "save-plan"`, "Waiting for Home Assistant to save the plan."; while `"run-plan"`, R6's reason; while work is stoppable, "Can't change this until the robot finishes."; when Home Assistant or the robot is offline (state.ts:728-729), "Waiting for Home Assistant to reach the robot again."; otherwise Save's reasons (state.ts:1008-1023).
  - **Result.** Success shows "Plan turned on" or "Plan paused" inline + toast and reloads the catalog in place, so the preview follows. A failed send or a failed pre-send reload reverts the switch, shows `v4_notice_plan_save_failed` inline + toast, and returns `command` to idle (§9; today effects.ts:2604 leaves `"failed"`, which gives "Check robot status" at state.ts:874-884), so Run plan keeps its state. Focus stays on the switch after success and after failure.
- **Map.** In Run, taps never change the plan: `toggle-room` returns `state` when `planView === "run"` (state.ts:415-430; tap test at gesture-controller.ts:358-364). In Edit, a tap toggles the same room as its checkbox, with the same name. Tapping a row never changes its selection; only the checkbox or the map does. Map numbers match the list, in Saved order only (selection fill at renderer-controller.ts:1504-1513). Unticking a room parks its settings and schedule in the draft until Save. Parked rooms are not sent, so the save request is unchanged (effects.ts:2299-2324).
- **Order.** The segmented control patches `runBehavior`. Numbers and arrows appear only in Saved order (`C-OrderBadges`). An arrow moves its room one place and keeps focus. At either end the unavailable arrow stays in place, `aria-disabled`, and is described by "{room} is already first" or "{room} is already last" (the MS-STATUS-09 / MS-PLAN-13 rule in `design-system.md`). Focus therefore never moves. Each move is announced in the polite region (shell.ts:1576).
- **Expanded room and blocked jump.** This spec owns `WorkspaceState.expandedRoom: string | null`, the room open in Edit.
  - The disclosure button and `set-plan-view edit {roomId}` set it, and only one row is open at a time. A reselect of the open plan (effects.ts:2504) keeps it; leaving Edit clears it. Today only the Room schedule opens and closes, as a DOM `<details>` (workflow-panel.ts:489).
  - "Review {room}" opens that room, scrolls it into view and focuses its disclosure button. The schedule fix shows inline (`room-schedule.md`).
- **Navigation and focus.** Forward moves (picker row, plan card, Edit, Create) focus the h2 (shell.ts:554); Review focuses the target room. Backward moves (Back, Cancel, Done, Escape, Save success) restore the launcher: the picker row, the home plan card, or Run's Edit button (MS-KEY-01). After Delete, focus goes to the picker h2. Back and Escape from Run go to `planOrigin`.
  - Escape order: dialog → precision → Full map → `discardDraft` (dirty Edit) → Edit to Run (saved plan) or to the picker (new plan, and Cancel likewise) → Run to its origin → the picker to home. The plan step at state.ts:568 becomes view-aware and origin-aware.
  - `needsDraftConfirmation` (draft-navigation.ts) also guards `set-plan-view`. Discard returns to Run for a saved plan and to the picker for a new one; today it always goes to the picker (state.ts:391-399). A view change re-applies the starting detent (`shell.md` §5 Sheet); today only a workflow change does (shell.ts:545).
- **Stale preview.** Every exit from Edit either saves or discards, so Run never shows a dirty draft. Edit's preview section and `v4_next_run_preview_stale` (workflow-panel.ts:716) are retired.
- **Dialogs** (`shell.md` owns them; MS-DLG-02/03). `discardDraft` names the plan and offers Save when the draft is valid. `confirmDeletePlan` says only that automations that run the plan will stop working, and that the robot won't move (§6). When the plan is the default, it adds "{new_default} becomes your default plan.", or "You'll have no default plan." if it was the last plan. Deleting the default promotes the first remaining plan, or none (plans.py:2623-2624), and Home Assistant's plan buttons run the default (button.py:28-30).

Each variant is one whole string whose placeholders hold data only, never joined in code (`copy-style-0.5.md:97-99`); `{count} rooms` strings have `_one` forms ("1 room").

## 8. Accessibility
- **Targets:** the row checkbox, the disclosure button, the arrows, the overflow, the reason link and Run's switch row are all ≥44 px on coarse pointers, as separate targets.
- **Contrast:** Run plan, Save, the selected segment and the "Default" chip follow the `design-system.md` rule: keep HA's pair when it is ≥4.5:1, otherwise darken the fill or use a black label. The map's selection stroke and a selected row's border use `--ms-indicator`, ≥3:1 against the card and sunken surfaces (`design-system.md` §5). Due lines and warning or success text lines (the picker's line 3, reasons) use `--ms-text` with a tone glyph, never raw tone-coloured text (`design-system.md` §5), so they stay ≥4.5:1.
- **Forced colors:** primary buttons follow MS-DS-01. The selected segment uses Highlight/HighlightText (the pattern at controls.ts:186-190). Chips have text and a ButtonBorder outline, so no state relies on colour alone.
- **Reduced motion:** Run and Edit swap without a slide.
- **Screen readers:** each forward entry focuses the h2. The disabled Run plan reason is linked through `aria-describedby` (shell.ts:959-963). Notices follow `shell.md` (live region at shell.ts:1576). A reorder announces "{room} moved to position {position}", and the end arrows say why they are unavailable. The "Unsaved changes" chip sits inside the h2. The disclosure exposes `aria-expanded`, and the checkbox is named "Include {room}".
- **RTL:** back and disclosure chevrons mirror; the vertical reorder arrows do not. Switch knobs use a logical translate (MS-PLAN-20, controls.ts:153). Names render in `<bdi>`, and numbers use `Intl.NumberFormat`.

## 9. Backend needs
- **Backend need:** add `next_run_estimate_seconds: int | null` to each plan in the plans projection, owned by `custom_components/matic_robot/slam_scene.py:1431-1448`.
