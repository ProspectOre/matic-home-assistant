# HA-native flows and Repairs: redesign spec (0.5)

Phase B spec for Home Assistant's own dialogs: add robot, Reconfigure, reauth, the identity-changed Repair and its recovery, options, three Repairs. Entities, actions, blueprints, LLM tools and events are in `docs/ux-spec-0.5/ha-entities.md`. Audit: `docs/ux-audit-0.5/ha-native.md`, `copy.md`, `copy-corpus.tsv`; "CP-nnnn" means that row's `proposed_rewrite` is final text unless a row here overrides it, and `docs/copy-style-0.5.md` wins over both. Cites are to base `c00f878`. The integration is "Matic (Unofficial)" (`manifest.json:3`); Reconfigure and Configure are in the entry's ⋮ menu under Settings > Devices & services > Matic (Unofficial). Keys, unique_ids and policy stay; copy, flow structure and section 9 change.

## 1. Scope
- Surfaces: add-robot flow, Reconfigure and reauth, **new identity recovery** (Repair fix flow plus one config-flow step), options flow, three Repairs. No Map Studio (`ms-*`) or shell work; entities, actions, blueprints, LLM and events are `ha-entities.md`.
- Audit IDs (25): HA-FLOW-01, -02, -03, -04, -05, -06, -07, -08, -09, -12, -13, -14, -15; HA-OPT-01, -02, -03, -04, -05, -06; HA-REP-01, -02, -03, -04, -05, -07 (full IDs in section 11). The other 27 IDs (HA-ENT, HA-SVC, HA-BP, HA-LLM) moved to `ha-entities.md`.
- Owner decisions touched: recovery is a fresh Bluetooth re-pair and the pin is never relaxed (binding, section 5); "Advanced" options entry.

## 2. User goal
A household administrator adds a robot, or repairs its connection, through Home Assistant's own dialogs. In two seconds they see which robot it is and the one thing needed from them (usually: turn on Pairing mode and type the code); in a Repair they also see that plans and history are safe.

## 3. Hierarchy (flow and step order; Stop is in no flow here)
1. Add robot: `user` (progress `discovering`) > none found `discovery_failed` menu [Search again, Enter address manually] / one found `pair` / several `select_robot` (configured robots omitted) > `pair` (empty confirm step) > progress `wait_for_pairing` > `connecting` > `pairing_code` > progress `verifying` > entry titled with the robot's name. `manual` checks the address only (no Bluetooth call), then `pair`. A failure returns to the same form with one inline error.
2. Reconfigure (⋮ menu): menu [Update robot address, Pair Home Assistant again, Robot was reset].
3. Identity recovery: Repair Fix > fix-flow `init` > hand-off > `recover_identity` (Reconfigure source; pre-flight, then pairing) > progress > `pairing_code` > progress `verifying` > abort `identity_recovered`.
4. Options (⋮ > Configure): [Choose the default plan, Reset room cleaning history for one plan, Reset room cleaning history for all plans, Advanced, Done]; each reset has one named confirmation; the dialog ends with a message naming what changed. Not connected: abort `entry_not_loaded`.

## 5. Interaction
- Close at any point cancels: `async_remove` cancels the pairing task and the pending passkey request (`config_flow.py:293-300`); nothing is written and an open Repair stays. HA moves focus to the first field of each step.
- Named dialogs (the title asks and carries the object; the destructive button is the bare verb, `copy-style-0.5.md:90`): "Remove the robot's saved pairing?" / "Remove"; "Reset history for {plan_name}?" and "Reset history for all plans?" / "Reset" ("This can't be undone"). Reversible: pairing. Not reversible: history reset.
- **Identity recovery, binding rules (security).** Any failure leaves the old pin, old credential and Repair untouched; `entry.data` is written once, in step 5. Refusing a different serial is an invariant (section 12).
  1. Pre-flight, before the code step (no passkey, no write, old pin not needed): fetch the certificate at the form's address through the Matic-CA context (`tls.py:36-47,106-129`); `validate_certificate(cert)` with no expectations returns the presented identity after role and SAN checks, and `fingerprint=None` skips the pin compare (`tls.py:75`); the flow compares `identity.serial_number` with the stored serial itself, because serial, hostname and role mismatches all raise the same `InvalidRobotCertificateError` (`tls.py:94-101`); then it calls `validate_certificate` again with the stored hostname and serial, which can now fail only on the normalized hostname (`tls.py:61-63,96-99`). Results: other serial = `different_robot`; role or hostname failure = `invalid_certificate`; unreachable = `recover_cannot_connect`. A failed Matic-CA check also lands in `recover_cannot_connect` today, because `ssl.SSLCertVerificationError` is an `OSError` and the fetch maps every `OSError` to `CannotConnectError` (`tls.py:128-129`); a recovery-flow-only wrapper around the fetch (section 9) reports it as `invalid_certificate`, so the user is not told the robot is unreachable when the certificate is the problem. The shared fetch and the runtime connect path stay unchanged (section 12). Both fail closed. Analogues: `config_flow.py:834-844`, `1104-1109`.
  2. Fresh passkey: pairing runs through `_async_reauth_credential` with `replace_existing_bond=True` (`config_flow.py:671`; `bluetooth_pairing.py:437`), so BlueZ removes any existing bond and a new code is required (`bluez_agent.py:227-231`).
  3. Gate, fail closed: accept the new credential only if all of these facts belong to the Bluetooth candidate that issued it: it paired through the scoped BlueZ session with a device path (`pair_with_bleak` false, `bluetooth_pairing.py:386,396`); `bluez_session.reused_existing_bond is False` (`bluez_agent.py:225-233`; read at `bluetooth_pairing.py:491`); and its agent requested a passkey and a code was submitted (`passkey_exchange.requested`, `.submitted`, `bluetooth_pairing.py:107-114`). The gate does not rely on "bleak never asks for a passkey", because the scoped agent is also BlueZ's default agent (`bluez_agent.py:296-302`). A missing or unattributable fact counts as not fresh: abort `pairing_not_confirmed`. Today the flow sees none of this (`bluetooth_pairing.py:332-341`) and the passkey facts are per attempt, not per candidate: one exchange serves every candidate (`:371-378`), `requested` and `submitted` are never reset (`:106-139`) and `cancel()` does nothing once the passkey is set (`bluetooth_pairing.py:141-145`, called at `bluez_agent.py:312-313`). Section 9 lists the change.
  4. Pin: fetch again after the credential exists and run `validate_certificate` with the stored hostname and serial (no fingerprint). The new fingerprint is the one from that fetch connection. The authenticated connection is a separate `MaticHermesClient` built with the new credential and pinned to that fingerprint (`api.py:484-492`), so its `Handshake` is authenticated (`api.py:516,649-657`; skipped without a credential, 654-655), never a bare `GetBotInfo`; `async_get_info` must return the stored serial (`config_flow.py:842-844`). Errors: rejected credential = `recover_credential_rejected`, unreachable = `recover_cannot_connect`, pin or serial failure = `invalid_certificate`; each leaves the old pin.
  5. Write, one step: `async_update_reload_and_abort` with fingerprint, credential and changed host or port, then `ir.async_delete_issue(hass, DOMAIN, f"robot_identity_changed_{entry_id}")`. HA core deletes a Repair only when its fix flow ends with create-entry, not abort, and the reloaded coordinator starts with `_identity_issue_active=False`, so its clear path returns early (`coordinator.py:157,961-962`): the delete is explicit.
  6. The runtime pin check (`tls.py:74-76`, `coordinator.py:475-480`) is never disabled or deferred and nothing "trusts on next connect". `update_address`, `replace_local_access` and the coordinator keep demanding the old pin (`config_flow.py:827-833`) until step 5. Only the old-fingerprint comparison is absent in steps 1 and 4, because its mismatch is the reason for recovery (Decision 1).
  7. Trust limit, stated plainly: `Handshake` sends the credential to the endpoint (`api.py:657,2106-2110`), so it authenticates Home Assistant to the endpoint and proves nothing about the endpoint. The endpoint binding is the Matic CA plus the stored serial and stored hostname, the same trust as first setup; the Bluetooth peer is not matched to the serial (candidates are chosen by advertisement and signal, `bluetooth_pairing.py:278-286,371`). Residual risk: a host holding a Matic-CA key for this serial and hostname (for example a retained pre-reset key) would be re-pinned and receive the new credential. This is a limit, not a relaxation; the owner signs it off under Decision 1.
- Hand-off: `init` ends with `async_abort(reason="continue_in_reconfigure", next_flow=(FlowType.CONFIG_FLOW, flow_id))` only if `"next_flow"` is in `inspect.signature(RepairsFlow.async_abort).parameters`, and `FlowType` is imported inside that same guarded branch so an older core still loads `repairs.py`; the abort text always names the manual path, because the frontend half cannot be detected (Decision 2).
- Reused: `_show_pairing_form` (302), `_async_start_pairing`, `_async_reauth_credential`, `_async_pairing_progress`, `pairing_code`, `finish`. Not reusable: `_async_reauth` and `_async_verify_existing_robot` (they demand the old pin, 697-748, 819-844) and the only pin write, entry creation (1126). Plans, areas and history are keyed by serial and survive a re-pin; removing the entry erases them (`__init__.py:724-741`, `plans.py:1614-1635`).

## 7. Responsive
Home Assistant renders every flow and Repair as a dialog: full-screen on phones (320, 360, 390, 844x390 landscape) and a centered card on tablet and desktop (600 to 1440). This spec adds no layout, so nothing is pinned or off-screen. Keep a description to two sentences plus the numbered steps (six lines at 320), one idea per paragraph, no tables, so the submit button stays visible; the identity Repair body stays about 400 characters or fewer.

## 8. Accessibility
HA's dialog supplies 44 px targets, focus order, forced-colors, reduced-motion and live announcement of form errors and progress text; add none, and no custom colours (HA theme tokens keep contrast). Errors are inline form alerts (not colour only); progress text names the stage; the code field is numeric with `one-time-code` and its 20 s window is in the text, never a colour-only countdown. Strings use placeholders and numbered lists so translators can reorder and RTL mirrors.

## 10. Decisions needed
1. **Security sign-off for re-pinning.** No existing step can re-pin: `_async_verify_existing_robot` requires the old pin (`config_flow.py:827-833`) and the pin is written only at entry creation (1126). Section 5 reuses the pairing steps and adds one pre-flight, gate and verify-and-write step that equals first setup plus the stored identity, a fresh passkey and an authenticated handshake. Stated limit to sign off: `Handshake` authenticates Home Assistant to the endpoint and proves nothing about the endpoint, and the Bluetooth peer is not matched to the serial; the binding is the Matic CA plus the stored serial and hostname, the trust of first setup, so a host holding a Matic-CA key for this serial and hostname (for example a retained pre-reset key) would be re-pinned (section 5 step 7). Recommended: approve after a security review before build; otherwise ship only the interim remove-and-re-add text.
2. **Hand-off when `next_flow` cannot open from a Repairs abort.** Default: the fix flow aborts with text naming ⋮ > Reconfigure > Robot was reset on every supported version, and adds `next_flow` where feature-detected. Alternative: raise the minimum Home Assistant (`hacs.json:3`) to the first core and frontend release that opens it (not known here).
3. **Where the pairing steps run.** Hand off to the Reconfigure flow (steps reused unchanged) or host them inside the Repair dialog (needs the pairing code in a shared mixin). Recommended: hand off.
4. **Address field in recovery.** Update robot address still works when a robot moved with its certificate unchanged (the Repair offers it); it cannot work once the certificate changed, so without the field a reset robot that also moved dead-ends. Recommended: include the collapsed section.
5. **Moving plans to a replacement robot (later).** Plans are keyed by serial; 0.5 refuses (section 12). Recommended: no data migration in 0.5; revisit with its own design.
- **Owner decisions (2026-10-11):** all recommendations accepted. D1 re-pin after a fresh passkey pairing, approved subject to the security review before the UX6 build; D2 the abort names the Reconfigure path and adds `next_flow` where feature-detected; D3 hand off to Reconfigure; D4 include the collapsed address section; D5 no plan migration in 0.5.

## 12. Invariants kept / out of scope
- Kept: local-only operation, pinned transport, administrator-only Matic Map, unique_ids and entity_ids, policy in `state.ts`. **Unchanged, binding:** the shared certificate fetch, first setup, `update_address`, reauth and above all the coordinator's runtime connect path (`coordinator.py:475-476`, `api.py:506-507`); the CA-failure reporting lives only in the recovery wrapper, so a non-Matic host on the network can never raise the identity Repair. **Refused, binding:** a robot with a different serial is never re-pinned onto this entry (`different_robot`, section 5 step 1); it is added as a new robot and plans do not move (Decision 5).
- Out of scope: Bluetooth proxy pairing, robot-model detection, plan migration, any `ha-*` or `mwc` rewrite.
- Cannot verify here: `next_flow` on a Repairs abort at the declared minimum 2026.7.0 (`hacs.json:3`; installed core 2026.9.3 accepts it in `repairs/models.py`, the frontend half is untested); that the robot's `Handshake` rejects a credential issued for a different robot (firmware behaviour; UX6 physical acceptance verifies it before the slice ships); whether a factory reset changes the hostname (recovery keeps the stored-hostname check); whether the Matic advertisement carries the serial, which a later design could use to bind the Bluetooth peer to the serial.
